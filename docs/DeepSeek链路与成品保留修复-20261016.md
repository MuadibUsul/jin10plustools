# DeepSeek链路与成品版本保留

## 已确认根因

- 团队DeepSeek Key可被worker读取；配置模型为`deepseek-v4-pro`。
- `produce`命中同日期缓存直接return，连旧的`not_configured/invalid_response`一起复用。
- 请求只有768 tokens、未显式关闭思考，且不同失败被合并为`invalid_response`，没有结束原因与用量，旧失败无法据此反推唯一原因。
- 规则稿有效就被标记成功，主界面未区分AI失败。模型结果默认单独保留，需要编辑采用。

## 修改

- 页面只返回、显示最新成品，移除历史版本选择器。
- 每团队、栏目、生产日期最多保留两份可下载成品版本；新增时自动裁剪，既有超量版本一并整理。被裁剪版本的注释记录保留在团队归档，原始来源与图表快照继续保留，供复现。已被裁剪的旧确认状态撤销，不把确认自动转给新稿。
- 同日期数据、图片继续复用；AI未成功、未生成或模型变更时，普通生成继续补做AI；成功且模型未变时避免重复请求。
- 请求显式`thinking.type=disabled`、输出4096 tokens、超时60秒。保留模型、结束原因、用量和稳定错误分类，不保存Key、请求头或模型思考正文。
- 保持事实安全：模型只能选择已核验候选文字；数据、图表和固定注释不由模型任意改写。
- 卡片与终端区分AI已完成和规则稿已保存但AI未完成。AI文字仍需编辑点击采用并保存。
- 测试：后端全套131项通过，4项因缺独立PostgreSQL测试库跳过，1项断言适配最新API后专项4项通过；前端全套56项通过，最终脚本专项13项通过，typecheck与lint通过。

## 验证入口

- `deploy/check_deepseek_repair.py`：对今天五个栏目使用既有快照补做实际AI请求，检查模型、结束状态和用量，然后验证各期最多两份成品。
- `tests/test_deepseek_chain.py`：覆盖请求参数、截断诊断、缓存补跑、成功复用、两份保留和仅最新可见。

## 正式上线验证

- API和固定快讯worker均已更新为`plus-api:deepseek-repair-20261016`。
- 10月16日五个栏目使用既有快照实际调用`deepseek-v4-pro`，全部返回`ok`，结束原因均为`stop`，有实际用量记录。
- 正式接口逐项验证：仅返回最新一份，数据库每期两份成品；各栏目图片下载成功且不超过266000字节。原始来源与图表证据继续保留。
- 统一站点路由、登录、选稿、素材同步通过；实际日报PPTX和PDF导出7页，无警告。
