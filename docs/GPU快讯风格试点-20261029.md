# GPU 快讯风格试点（2026-10-29）

## 范围与上线边界

本次以固定快讯 `gpu_rental`（AI 景气度指标）试点。新模块只消费已校验的事实包，输出候选标题、动态正文及结构化生成记录。它不抓取行情，不计算或回写观测，不生成图片，不改固定图注，不确认或发布快讯。

其他固定快讯、新鲜事、注解辅助继续使用原有流程。现有团队自定义正文模板和团队 Skill 设置优先；试点不得静默覆盖这些设置。现有 AI 供应商、实际模型识别及失败回退边界保留。

默认使用 `shadow` 模式：旧流程的标题、正文、事实、图片和固定说明保持原样；新候选只作为并行记录保存。程序硬检查通过仅表示该候选通过当前实现的检查，不等于经过编辑验收。

模式由环境变量 `PLUS_BRIEFS_GPU_EDITORIAL_MODE` 控制：

| 模式 | 行为 |
| --- | --- |
| `off` | 不运行新候选流程 |
| `shadow` | 生成候选和诊断，保留现有正式稿 |
| `active` | 仅在风格包经审核、配置适用且候选通过检查时采用新稿；失败保留完整旧稿 |

风格包初始状态为 `draft_pending_editor_review`。仅当包状态为 `approved`、审核人 `review.approved_by` 和审核时间 `review.reviewed_at` 均非空时，才允许 `active` 接管；同时应记录盲评记录位置。未审核的包即使被配置为 `active`，也只能继续影子运行，并记录 `pack_not_reviewed`。不要为了观察效果把包直接标成已审核。

本次交付不执行生产部署，不修改服务器配置。任何生产切换应在离线验收、并行试跑和回退检查后单独进行。

## 原始资料、生产表达与验收资料

原始范文仍保留在 `skills/jin10-plus-gpu-rental-text/references/history.md`，作为有来源的历史档案；不改写历史日期、数字或旧口径。生产表达另存为版本化风格包：

`skills/jin10-plus-gpu-rental-text/production/style-pack.json`

风格包的场景、句式、例子和审核状态与原始档案分开。旧范文出现的供应紧缺、需求迁移、历史新高等说法，不能仅因被写入旧稿就成为今天的事实。生产句式必须满足当前事实前提。

候选记录包含包版本、包内容哈希、事实包哈希、场景、表达计划、使用范文 ID 和硬检查结果。它不保存 API 密钥、请求头或登录资料。记录进入现有快讯版本的 JSON payload，因此可沿用现有团队隔离、不可变版本与数据库导出，无需新增表。

现有日期缓存保持 pre-Skill 规则稿。候选记录不应回写成可复用的正式稿；本次运行结果与版本 payload 才是对照记录。生成签名必须覆盖新风格包内容，不能只靠手动版本号判断缓存新旧。

## 写作与事实约束

1. 先确定 B200、H100、A100 同一数据日的价格、各自周变化口径及可用历史比较，再选择主旨和表达。
2. 指标、价格、单位、方向、基准日构成完整绑定，不允许模型把数字分配到另一张卡。
3. 并列高点只写并列；“高于此前已收录高点”不扩展为未单独验证的历史或半年新高。
4. 某张卡缺周变化基准时，保留价格并明确说明缺口，不补值，也不据不完整方向写代际分化。
5. 公开卡片的七日变化与可见历史价格计算值保留来源差异；计算值不能伪装成指数精确涨跌幅。
6. 模型可选的是满足当前事实条件的表达模块 ID，程序负责填值和拼接。格式正确、JSON 合法、数字集合相同均不足以单独证明事实正确。
7. 新模块失败、包文件错误或候选检查失败时保留完整旧稿。已审核的 active 流程在 AI 不可用或选择失败时，使用经审核包的确定性完整组合，并记录 `deterministic_fallback`。影子流程不新增外部模型调用。

## 离线回放与人工盲评

离线工具：`jin10-server/tools/evaluate_gpu_editorial.py`。

默认用例：`jin10-server/tests/fixtures/gpu_editorial_cases.json`。用例分 `development` 与 `holdout`，覆盖正常方向、并列/突破/接近高点、缺失基准、非法或冲突字段，以及公开/历史计算/混合/人工来源。当前用例是明确标注的合成场景，用于安全边界和覆盖回归；不能称为真实行情回放，也不能据此声称编辑直接采用率已达标。

在 `jin10-server` 目录运行，例如：

```powershell
..\.venv-news\Scripts\python.exe tools\evaluate_gpu_editorial.py --out E:\daylycontents\outputs\gpu-editorial-review-20261029
```

工具只读用例、风格资产和代码，不访问网络或数据库，不调用模型，不覆写生产资料。`--out` 必须是尚不存在的新目录；脚本拒绝输出到 `app`、`tests`、`skills` 或 `deploy` 中。可用 `--cases` 指定另一份同结构用例、用 `--seed` 固定匿名排列。

输出文件：

| 文件 | 用途 |
| --- | --- |
| `blind-review.md` | 人工阅读的匿名 A/B 标题和正文；不标出新旧稿 |
| `blind-review.json` | 同一组匿名稿与空白人工评价字段 |
| `review-key.json` | 单独保存用例、A/B 新旧映射，盲评结束前不要交给评审 |
| `evaluation.json` | 场景数、独立断言、拒绝原因和版本记录；不自动判风格合格 |

A/B 位置和样稿顺序由稳定种子打散。预期应拒绝的无效事实包不进入双稿盲评；它们仍进入硬检查报告。工具将“预期应拒绝却生成候选”“预期有效却被拒绝”“其他独立断言失败”分别记录，避免把正确拒绝计成事实错误。

盲评请记录每稿：可直接采用、仅需微调、需要实质改写，以及具体原因。程序中的 `human_direct_acceptance_rate` 与 `style_accepted` 保持空值，直到取得人工结果。测试集中的关键事实错误零容忍是这批用例的验收要求，不代表未来生产绝不出错。

可在 `blind-review.json` 的 `human_review` 中填写 `preferred`（`A`、`B`、`tie`），以及 `A_readiness`、`B_readiness`（`direct` 可直接采用、`minor` 仅需微调、`rewrite` 需要实质改写）和修改原因。再次运行工具时用 `--reviews` 指向填写后的文件，并另选新输出目录。工具核对风格包哈希和逐稿内容，拒绝把旧稿评分套在新稿上；统计实际评分数量和直接采用率，未评分项不计入分母。`style_accepted` 仍由编辑的发布决策确定，工具不会自动签署风格包。

## 后续验收与推广

先由编辑审核生产范文和场景表达，再补充具有明确来源的真实事实包，保留日期与修订，不把未来事实泄漏进当期输入。真实盲评需把范文与留出用例分开，记录样本数、每个场景的结果与必要的重复运行，不能只报告平均分。

在约定的直接采用率、事实检查及运行稳定性门槛达到后，才签署风格包并进行有限范围切换。每次改包、改模型或改变组合规则都回放同一套留出测试；编辑改稿及原因进入下一版素材候选，不能自动把所有改稿当成新的正确答案。

回退方式是恢复 `shadow` 或 `off` 并重新生成后续稿件，不删除历史版本、不覆盖已确认稿。原始素材、既有团队模板和正式数据继续保留。
