在原仓库中执行，先确认本机未提交改动已保存：

```bash

```

## 合并

审阅后在干净工作区合并；本次交付没有代为合并main：

```bash
git switch main
git pull --ff-only origin main
git merge --no-ff feature/fixed-briefs
```

若main已推进，先在feature分支合并最新main并重跑测试，重点检查`main.py`页面注册、models注册、Compose及Alembic迁移。当前新迁移是`0007`、父版本`0006`；若另一分支也新增迁移，应重新编号或增加Alembic merge revision，禁止直接覆盖对方迁移文件。

确认合并无误后再自行推送main。也可以在GitHub发PR，审阅通过后按团队流程合并。

## 目标服务器部署

本次没有改服务器、Caddy、生产数据卷或账号。服务器沿用原项目的共享Caddy和`deploy/docker-compose.yml`，不要把本地开发Compose直接覆盖线上部署配置。

1. 先备份PostgreSQL与storage卷，确认共享服务器可容纳额外1GB内存上限/1核worker；镜像首次构建会安装Chromium及绘图库。
2. 将更新后的代码、部署Compose交付到现有服务目录；保留目标服务器原有`.env`，不要用`.env.example`替换真实配置。
3. 可选加入`PLUS_BRIEFS_DEEPSEEK_API_KEY`、`PLUS_BRIEFS_DEEPSEEK_MODEL`。留空时规则线完整运行，不请求模型。
4. 沿用既有项目部署路径与网络，先启动db/api完成迁移，再启动worker：

```bash
docker compose up -d --build db api
docker compose exec api alembic current
docker compose up -d --build brief-worker
docker compose logs --tail 80 brief-worker
```

目标版本应为0007。worker等待api健康检查通过后启动；它不在API进程内运行，默认所有团队自动排期关闭。不要手动多启worker；数据库会话锁限制同一数据库单个生产worker。

5. 访问`/`、`/daily/`和`/briefs/`，使用既有账号登录。先验证日报采集、选稿和PDF正常，再测试快讯。
6. 工作时间外通过“测试运行”手动取数；正常生产按钮仅当日工作日08:00—10:00有效。网页浏览本身不抓取外部来源。
7. 可导入随代码提供的历史样稿，测试五栏目界面，无需联网：

```bash
docker compose exec api python -m app.briefs.cli import-samples --team "你的现有团队名"
```

样稿在生产日期选择器切到`2026-10-15`查看。它们有明确“历史样稿/测试稿”提示，不会自动确认；重复导入会产生新版本，不覆盖旧版本。

8. 查看估值/原油ETF的来源说明，编辑并核对标题、完整正文、图像；确认后用viewer验证只能取已确认版本。自动任务结束也不会自动确认或发布。
9. 最后由admin在固定快讯页面“启用自动排期”。工作日08:00—10:00，完成即停；不维护中美假期表，仅核对目标数据日。
