## A01 · P1 · 估值后台补抓混用了制图结果

位置：[sources.py:391](<E:/daylycontents/jin10plustools/jin10-server/app/briefs/sources.py:391>)、[run_erp.py:470](<E:/daylycontents/jin10plustools/jin10-server/app/briefs/engines/valuation/run_erp.py:470>)、[worker.py:361](<E:/daylycontents/jin10plustools/jin10-server/app/briefs/worker.py:361>)。

`reconcile` 将 `DATA_COLLECTION_ONLY=1`。ERP 引擎在 `data_only` 下返回 `data_ready=True`、`image_generated=False`，按设计不提供 `image_path`；适配器通过数据就绪检查后仍无条件访问 `result['image_path']`，抛出 `KeyError`。

复现：模拟已核验的两日 ERP 和总市值输入，不发网络请求、不绘图，调用真实 `sources.valuation()`，得到相同异常。生产近两日也有多条估值 `reconcile` 的 `error="'image_path'"`，包括 11 月 4 日 18 点左右的补抓任务。

影响：后台补抓不能正常完成、状态被记为失败、来源校验不形成成功基线。部分历史文件和结构化观察会在报错前或归档阶段保留，因此不能据此断言整段历史数据丢失。正常制图路径与这条后台路径不同，当前估值新稿成功不代表补抓已经正常。

修复边界：只有制图模式读取或复制图片；采集模式应独立返回有效数据载荷并正常完成来源入库。用真实数据模式契约做回归，不改估值图的冻结版式。

## A02 · P1 · 普通生成没有保护开始后的人工修改

位置：[worker.py:202](<E:/daylycontents/jin10plustools/jin10-server/app/briefs/worker.py:202>)、[worker.py:488](<E:/daylycontents/jin10plustools/jin10-server/app/briefs/worker.py:488>)、[worker.py:506](<E:/daylycontents/jin10plustools/jin10-server/app/briefs/worker.py:506>)。

图片重绘和原油自动后续刷新已有开始版本保护，但普通 `produce/refresh` 没有通用的开始版本检查。最终拿到行锁只能串行分配版本号，不能证明当前稿仍是任务开始时的稿。

复现：v1 开始刷新；模拟 runner 运行时另一会话保存人工标题和正文为 v2；任务结束后写入生成稿 v3，当前版本回到任务的生成内容。v2 当时仍保留，属于当前稿被覆盖，并非立即物理删除人工版本；后续保留策略可能进一步使找回变困难。

修复边界：对每种会替换当前稿的任务绑定开始版本；完成时做条件提交。发现人工修改后保留编辑成果并报告冲突，不能把“增加了新版本”当作没有覆盖。

## A03 · P1 · 来源更正摘要并未覆盖全部成品依赖

位置：[product_inputs.py:12](<E:/daylycontents/jin10plustools/jin10-server/app/briefs/product_inputs.py:12>)、[data_reliability.py:76](<E:/daylycontents/jin10plustools/jin10-server/app/briefs/data_reliability.py:76>)、[data_reliability.py:96](<E:/daylycontents/jin10plustools/jin10-server/app/briefs/data_reliability.py:96>)、[briefs.py:275](<E:/daylycontents/jin10plustools/jin10-server/app/api/briefs.py:275>)。

`publication_digest` 从历史覆盖用的 `extract()` 生成。覆盖检查需要的序列集合，不等于成品使用的完整输入：流动性只收 DR001／DR007 加权利率，遗漏央行逆回购利率、投标／中标量和图中 DR014；算力只收价格及来源状态，遗漏公开披露／人工快照的周变化等文案输入。

复现一：只把央行利率 1.25 改为 1.30、操作量 5410 改为 8000、DR014 从 1.5 改为 2.5，摘要不变。复现二：Token 价格不动，公开周变化 -6.8 改为 -9.9，摘要不变。上述均为合成数字。

影响：后续补查即使识别并保存了这些输入变化，确认接口仍可能把旧正文／旧图视为来源未改。原始文件有归档不能弥补确认门禁漏检。

修复边界：为各栏目定义完整、版本化的成品依赖契约，区分归档清单、覆盖指标与发布输入；所有影响文字、图、日期或比较口径的字段都进入语义摘要。

## A04 · P1 · 失败检查能取消已知的更正阻断

位置：[briefs.py:277](<E:/daylycontents/jin10plustools/jin10-server/app/api/briefs.py:277>)、[briefs.py:288](<E:/daylycontents/jin10plustools/jin10-server/app/api/briefs.py:288>)。

确认接口只读取同栏目、同数据日按时间最新的一条 `BriefDataCheck`，并仅在其 `current_data_valid=True` 时比较摘要。于是最近一次网络／抓取失败，能遮蔽更早但已经核实的来源更正。

复现：稿件保存摘要为 old；保存一次成功更正检查 corrected，调用真实确认 API 返回 409；再插入一次较晚的失败检查，再确认同一旧稿，返回 200。没有改变稿件或纠正后的来源。

影响：系统从“已知有更正，必须重做”退回“允许确认”，与更正保护目标相反。

修复边界：最近尝试状态和最近可信来源版本分开保存／查询；失败不能撤销已知更正。不是把每次临时抓取失败都一律阻塞已有有效成稿。

## A05 · P1 · 图片幂等上传缺少跨文件／数据库一致性

位置：[assets.py:53](<E:/daylycontents/jin10plustools/jin10-server/app/api/assets.py:53>)、[assets.py:66](<E:/daylycontents/jin10plustools/jin10-server/app/api/assets.py:66>)、[assets.py:81](<E:/daylycontents/jin10plustools/jin10-server/app/api/assets.py:81>)。

图片 ID 来自 URL，不能证明字节相同。两个并发请求都查到记录不存在后，先写相同最终文件路径，再插入数据库；失败方捕获唯一冲突并返回 200，但它此前已经覆盖文件。

复现：同一 URL 上传两张不同且有效的 PNG，控制交错后两请求返回 201／200，数据库 SHA 是第一张，磁盘实际是第二张。这里也有现成的原子文件替换，但原子替换不能保护数据库与文件的一致性。

影响：存档元数据、下载原图及预览可能不一致，无法按 SHA 证明素材；同一 URL 内容变化或同事并发采集即可触发。需要编辑权限，不是已证明的匿名文件写入。

修复边界：按团队和资源 ID 锁定首次建立流程，或采用字节摘要对象路径及事务后引用；唯一冲突时核实既有元数据，不能假设内容一致。

## A06 · P1 · 审核与当前草稿修订可能脱节

位置：[store.py:430](<E:/daylycontents/jin10plustools/jin10-server/app/news_skill_os/store.py:430>)、[store.py:445](<E:/daylycontents/jin10plustools/jin10-server/app/news_skill_os/store.py:445>)、[news_skill_os.py:476](<E:/daylycontents/jin10plustools/jin10-server/app/api/news_skill_os.py:476>)。

修订保存有 `expected_revision` 条件更新；审核没有等价约束。审核会话读 v1 后，另一编辑保存 v2，审核继续修改旧修订并把 draft 总状态改为 approved。

复现结果：`current_revision=2`、draft `status=approved`，但 v2 的 `review_status=pending`，被审核的是 v1。即便解决数据库交错，客户端审核请求也应明确提交编辑实际看过的版本。

影响：未审核的当前文稿在工作台显示已审核。当前没有自动对外发布，因此不把此问题描述为已经自动发布了未审稿。

修复边界：审核动作绑定明确修订号，在同一事务锁定／条件更新该修订及 draft 状态；版本变化返回 409。

## A07 · P1 · 扩展旧团队同步在切换账号后仍落库

位置：[syncService.ts:59](<E:/daylycontents/jin10plustools/jin10-extension/src/services/syncService.ts:59>)、[syncService.ts:105](<E:/daylycontents/jin10plustools/jin10-extension/src/services/syncService.ts:105>)、[LocalMaterialRepository.ts:36](<E:/daylycontents/jin10plustools/jin10-extension/src/services/repository/LocalMaterialRepository.ts:36>)。

拉取使用任务开始时捕获的 session；网络返回后、每次本地写入前和提交游标前没有再次确认当前会话。push 虽有团队检查，但 `break` 仅退出结果循环，不能取消后续整个旧任务。登录／登出也没有取消在途同步。

复现：团队 A 的 `fetchChanges` 未完成时切换 B；返回后当前 session 为 B，本地仍新增 A 的素材，并提交 A 的游标。列表只排除删除项，未按当前团队再次过滤，因此存在旧团队数据短暂暴露于新会话的窗口；下一次同步可能清理，不等于窗口不存在。

影响限于扩展本地会话和存储隔离，本轮未证明服务端 API 越权读取其他团队。

修复边界：会话世代／取消信号贯穿上传、推送、拉取及最终状态提交；以服务端＋团队划分本地数据及游标，UI 同时按当前作用域读取。

## A08 · P2 · 密码重置没有撤销登录态

位置：[cli.py:64](<E:/daylycontents/jin10plustools/jin10-server/app/cli.py:64>)、[security.py:41](<E:/daylycontents/jin10plustools/jin10-server/app/security.py:41>)、[deps.py:33](<E:/daylycontents/jin10plustools/jin10-server/app/deps.py:33>)、[config.py:19](<E:/daylycontents/jin10plustools/jin10-server/app/config.py:19>)。

## A09 · P2 · 扩展拉取仍有本地编辑覆盖窗口

位置：[syncService.ts:64](<E:/daylycontents/jin10plustools/jin10-extension/src/services/syncService.ts:64>)、[syncService.ts:67](<E:/daylycontents/jin10plustools/jin10-extension/src/services/syncService.ts:67>)、[LocalMaterialRepository.ts:57](<E:/daylycontents/jin10plustools/jin10-extension/src/services/repository/LocalMaterialRepository.ts:57>)。

先 `get()` 判定 `sync_status`，后 `save()`。仓库内部只是写操作串行，检查和写入不是同一个条件操作；中间保存的新本地修改仍会被服务器旧版覆盖。

复现：读取旧 synced 快照后，本地保存 `NEW EDIT`、标记 local；随后同步 save 写回 `SERVER OLD` 并标记 synced。新修改失去再次推送的机会。此前修过的 push acknowledge 保护不能覆盖 pull。

修复边界：将“若当前没有更晚本地修改才应用拉取结果”实现成仓库内的原子操作，并处理删除和去重索引。

## A10 · P2 · JEV 结果没有绑定分析输入版本

## A11 · P2 · AI 配置损坏会阻断无需 AI 的规则稿

位置：[team_settings.py:12](<E:/daylycontents/jin10plustools/jin10-server/app/services/team_settings.py:12>)、[team_settings.py:44](<E:/daylycontents/jin10plustools/jin10-server/app/services/team_settings.py:44>)、[worker.py:216](<E:/daylycontents/jin10plustools/jin10-server/app/briefs/worker.py:216>)、[ai/worker.py:111](<E:/daylycontents/jin10plustools/jin10-server/app/ai/worker.py:111>)。

团队密钥的 Fernet 密钥直接由 JWT 密钥派生。JWT 轮换或已有 token 损坏时 `provider()` 抛 `InvalidToken`；快讯 worker 在规则生成及可选 AI 回退保护之前调用它。禁用 provider 也在解密后才判断 enabled。

复现：用旧测试 JWT 配置保存合成 token，轮换 JWT，调用真实 execute，立即抛异常；job 仍为 running、没有业务错误，等待 7 分钟租约恢复后可能再次重复。JEV 的 eligible 团队遍历也缺少逐团队隔离，一个解密异常可能中断该轮其他团队处理。

生产只读核查中当前四个 provider 配置均可解密，此问题是明确条件下的故障，不是当前充值后 AI 仍不可用的证据。

修复边界：分离认证和密钥加密生命周期，提供有版本的密钥迁移；解密错误局限于可选 AI，规则／样本风格回退照常完成，禁用配置不应解密阻塞。

## A15 · P2 · 独占锁在数据库会话丢失后可能失效

位置：[worker.py:525](<E:/daylycontents/jin10plustools/jin10-server/app/briefs/worker.py:525>)。证据类型：静态风险，未重启生产数据库或做断连注入。

worker 只在进入主循环前通过专用连接获取一次 PostgreSQL 会话级 advisory lock，此后业务使用其他新会话，不再使用或验证持锁连接。若数据库重启或该后台会话被终止，锁释放；原进程可以在后续业务连接恢复后继续循环，而新 worker 又能获取锁。

影响条件：旧 worker 未退出且启动另一个 worker，可能同时操作共享的团队历史／缓存文件。单任务认领锁不能完全保护不同任务共同使用的文件。

修复边界：让锁连接失效直接终止原 worker，或以受监控租约／明确文件作用域锁替代；用隔离 PostgreSQL 测试模拟断连恢复，不能在生产库验证。

## A16 · P2 · PDF 转换超时可能遗留子进程

位置：[pdf.py:42](<E:/daylycontents/jin10plustools/jin10-server/app/ppt/pdf.py:42>)、[lo_convert.py:44](<E:/daylycontents/jin10plustools/jin10-server/app/ppt/lo_convert.py:44>)、[lo_convert.py:84](<E:/daylycontents/jin10plustools/jin10-server/app/ppt/lo_convert.py:84>)。证据类型：进程生命周期静态风险，未在生产制造超时。

外层 `subprocess.run(..., timeout=180)` 管理 UNO Python 包装进程；包装进程又启动 soffice。超时会杀包装进程，它的 finally 无法继续保证 `office.wait()/kill()`；外层没有进程组清理，soffice 可能留在容器内。

影响：遇到卡死或极慢转换，反复预览可能积累 CPU／内存占用，影响同容器其他接口。不能由此断言已存在匿名资源耗尽攻击或线上残留进程。

修复边界：整个转换进程树由父级管理，超时／取消时统一清理；限制转换并发，在实际 LibreOffice 的隔离环境中验证。

## A17 · P2 · 部署失败会遗留维护状态

位置：[drain-worker.py:9](<E:/daylycontents/jin10plustools/deploy/drain-worker.py:9>)、[drain-worker.py:37](<E:/daylycontents/jin10plustools/deploy/drain-worker.py:37>)、[actions-release.sh:85](<E:/daylycontents/jin10plustools/deploy/actions-release.sh:85>)、[actions-release.sh:138](<E:/daylycontents/jin10plustools/deploy/actions-release.sh:138>)。证据类型：静态失败路径，未执行失败部署。

drain 一开始就建立持久 `.brief-worker-drain` 标记；超时或被取消没有对应清理。主脚本在 worker 停止后，API 启动、健康检查或迁移校验失败都会退出，而 drain 标记只在很后面成功路径删除。

影响：部署失败可能同时留下停止的 worker，或让尚存活的旧 worker 永久跳过 schedule／claim。只有 API 健康无法发现自动生产停摆。

修复边界：定义每个失败阶段的 drain 所有权、清理和可见故障状态。对尚未替换服务的失败可以撤销本次 drain；替换中失败应明确报告待修复状态。保持用户“不备份、不自动回退”的要求，不以修复为由增加回滚镜像或重建其他服务。
